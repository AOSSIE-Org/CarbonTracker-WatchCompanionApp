## Findings

### Finding 1: Sensitive health data logged to Logcat — `wear/app/src/main/java/org/aossie/carbontracker/services/HealthServicesManager.kt:71`

- Severity: High
- Confidence: 0.95
- Category: data_exposure / insecure_logging
- Description: The code logs raw heart rate values to Logcat:
  - `Log.d("HealthServices", "Received heart rate data: $value")` (line 71). Writing raw health measurements to Logcat can expose sensitive personal health data to any process or user with access to device logs (e.g., via ADB or platform debugging tools). This violates the project privacy boundary (the app is local-first and privacy-focused) and the project's own guideline not to log health/activity data.
- Exploit Scenario: An attacker with temporary physical or debugging access to the watch (or a malicious app with elevated permissions or using adb access on a developer-enabled device) can read device logs and extract heart rate/time information. On some Android builds, log access is broadly available to debuggable apps or via backups/diagnostics, increasing exposure.
- Recommendation: Remove or redact health data from log messages. Replace with non-sensitive telemetry (e.g., `Log.d("HealthServices", "Received heart rate (redacted)")`) or remove the log entirely. Ensure no other code paths print heart rate, distance, calories, timestamps, or other health identifiers to Logcat in either debug or release builds. Consider gating any diagnostic logs behind a build-time debug flag and never enable them in production releases.

### Finding 2: Health/fitness records stored unencrypted in local Room database — `wear/app/src/main/java/org/aossie/carbontracker/data/database/ActivityEntity.kt:9`

- Severity: Medium
- Confidence: 0.85
- Category: insecure_storage / privacy
- Description: ActivityEntity stores sensitive health-related fields in plaintext in the app's Room database (fields include `heartRate`, `distance`, `caloriesBurned`, timestamps). The code does not use at-rest encryption for the database; data will be present on device storage in cleartext.
- Exploit Scenario: If an attacker gains access to the device filesystem (lost/stolen device, or a compromised backup, or a rooted device), they can read the SQLite file and extract historical heart rate and activity history. A leaked backup of the device or careless inclusion of the DB in backups could similarly expose the data.
- Recommendation: Evaluate whether at-rest encryption is required by your privacy policy and target threat model. If needed, use Android's EncryptedFile / EncryptedSharedPreferences or SQLCipher for encrypting the Room database. At minimum, document the risk and ensure users are informed in `PRIVACY.md` about local storage protections. Also ensure backups exclude the DB if backups are not intended to include health data.

### Finding 3: Wear Data Layer message handling trusts incoming messages and lacks input size/structure validation — `wear/app/src/main/java/org/aossie/carbontracker/services/WearListenerService.kt:145-151`

- Severity: Medium
- Confidence: 0.80
- Category: insufficient_input_validation / trust_boundary
- Description: The wearable message handler decodes incoming JSON from `messageEvent.data` without explicit validation or size limits:
  - `Json.decodeFromString<List<ExerciseAcknowledgement>>(String(messageEvent.data))` (lines ~148-151). Incoming message paths (`/requestHeartRate`, `/requestExerciseData`, `/markExercisesAsSynced`) are handled and the service performs data access and mutation (reading unsynced activities, marking records as synced).
- Exploit Scenario: A malicious or compromised paired phone (or another node that can reach the device via the Data Layer) could send oversized or malformed payloads, causing high CPU or memory usage during JSON decoding, or trigger unexpected exceptions. A compromised phone app could send crafted acknowledgements to cause incorrect `markSynced` calls (potentially desynchronizing server-side/state expectations) or request repeated heart-rate collection. While Wear/Phone pairing reduces exposure, the watch must still treat incoming messages as untrusted across the node boundary.
- Recommendation: Add robust input validation and bounds checking before decoding and processing messages: check `messageEvent.data` length against a conservative maximum, catch and handle decoding exceptions (already present, but ensure it's comprehensive), validate each acknowledgement's fields (range checks on `id` and `lastUpdated`) before acting, and consider authenticating the requesting node if stronger guarantees are required. Rate-limit expensive operations triggered by incoming messages.

### Finding 4: Potentially sensitive signing credentials present in local `wear/key.properties` — `wear/key.properties:1`

- Severity: Critical
- Confidence: 0.95
- Category: secrets_exposure / release_configuration
- Description: The file `wear/key.properties` in the repository root contains keystore information including plaintext passwords (`storePassword`, `keyPassword`) and a path to a keystore file. These are signing credentials for app release artifacts. If committed to version control, they would allow an attacker to sign APKs/AABs as the app owner and publish malicious updates.
- Evidence: The file content (local workspace) shows `storePassword=221bsherlY` and `keyPassword=221bsherlY` (lines 1--2).
- Exploit Scenario: If this file or the referenced keystore is committed or otherwise leaked (for example, included in backups or CI environment variables), an attacker could produce signed builds that are indistinguishable from official releases and distribute them. This enables supply-chain compromise and impersonation.
- Recommendation: Immediately ensure this file is not committed (check Git history). If the secrets were ever committed, rotate/replace the signing key (create a new keystore and update release process) and revoke any distribution channels that used the compromised key if possible. Remove the plaintext passwords and keystore from the repository; store secrets in a secure secrets manager or CI-protected variables. Keep `key.properties` listed in `.gitignore` (the repo already has `wear/.gitignore` referencing `key.properties`) and document secure key handling in release docs.

## Notes

### Note 1: `WearListenerService` is exported and uses the Wearable message intent-filter — `wear/app/src/main/AndroidManifest.xml:52-61`

- Category: design-tradeoff
- Observation: The `WearListenerService` is declared `android:exported="true"` with an intent-filter for `com.google.android.gms.wearable.MESSAGE_RECEIVED`. This is necessary for the Google Wearable message APIs to deliver messages to the app. The service being exported means it is reachable by the platform/other nodes that use the Wear Data Layer.
- Rationale: This appears to be a deliberate design choice because the Wear Data Layer requires the service be discoverable for messages from the paired phone. Still, exported components increase the attack surface; the code should treat messages from the Data Layer as untrusted (see Finding 3).
